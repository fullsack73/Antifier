# Stock Screener 부분 조회 복구

## 확인한 문제

- 제공 로그에서 custom 입력 1,911개(정규화 후 1,909개) 중 조회 성공은 207개였습니다.
- 로컬 custom universe 캐시의 205개 중 187개는 A, 18개는 B로 시작했습니다.
- custom ticker를 정렬해서 조회한 뒤, 일부만 성공해도 해당 DataFrame을 전체 universe처럼 재사용했습니다. 이후 검색은 누락 종목을 다시 조회하지 않았고 UI도 조회 범위를 표시하지 않았습니다.
- 외부 공급자의 요청 제한/인증 오류가 조회 누락의 후보 원인입니다. 제공 로그에는 개별 실패 원인이 없어 특정 upstream 오류로 단정하지 않습니다. Finviz connection pool 경고만으로 Yahoo 요청 제한을 확정하지 않습니다.

## 변경

- 기존 부분 캐시의 성공 종목은 보존하고, 이후 검색은 누락 종목만 조회·병합합니다. 모든 재조회가 실패해도 성공 캐시를 덮어쓰지 않습니다.
- predefined group도 동일한 캐시 경로를 사용하며 예전 전체 group 캐시는 사용하지 않습니다.
- 유효한 지표가 없는 응답을 성공 종목으로 집계하지 않고, 기존 캐시의 점수가 없는 행도 재조회 대상으로 처리합니다.
- 동시 종목 조회를 6개에서 2개로 줄였습니다. 요청 제한 해소를 보장하는 조치는 아니며, 정상 대규모 조회는 더 느려질 수 있습니다.
- API의 기존 결과 배열은 보존합니다. `include_coverage=true` 요청만 결과와 필터 적용 전 조회 범위를 반환합니다.
- 한/영 화면에서 부분 조회 경고를 표시하고, 서버 로그에 누락 수와 예시를 남깁니다.

## 검증

- 스크리너·ticker 정규화·재무 점수 관련 백엔드 테스트 25개 통과.
- 기존 배열 응답 및 coverage opt-in API 테스트 2개 통과.
- 누락 경고와 완전 조회 후 경고 해제 화면 회귀 테스트 추가. 전체 프론트엔드 테스트 30개, lint, production build 통과. Plotly 번들 크기 경고는 남아 있습니다.
- 실제 1,909개 외부 종목 전체 재조회와 공급자 복구 여부는 검증하지 않았습니다.

## 후속 수정: 응답 호환성과 CSV 중복

- 이전 배열 응답을 보내는 실행 중인 서버와 새 프론트엔드가 만나는 경우 `data.results`가 undefined가 되어 화면이 중단될 수 있었습니다. 배열 및 coverage 객체 응답을 모두 처리하고, 잘못된 응답은 기존 오류 안내로 처리합니다.
- CSV 업로드 시 ticker를 대문자로 통일하고 중복을 제거하여 `AGX`, `AII` 같은 중복 React key 경고와 잘못된 업로드 개수를 방지합니다.
- 두 응답 형식, 잘못된 응답 3종, CSV 중복의 표시·전송 회귀 테스트를 포함해 프론트엔드 테스트 35개, lint, production build가 통과했습니다. 실제 브라우저에서 CSV 재업로드·검색은 미검증입니다.
